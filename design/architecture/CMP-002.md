# Responsibility

`tools/traceability/validate.py` resolves each current T1/T2 task's declared
implementation paths against the post-change workspace after schema validation.
It obtains task identity, level, and lifecycle status from the canonical graph and
frontmatter registry. It reports the task ID and failing pattern on failure.

Literal entries are checked directly; glob entries use Python pathlib glob
semantics (`*`, `?`, character classes, and recursive `**`). Only existing files
whose resolved paths remain inside the repository qualify. Git metadata is not
implementation evidence. Git tracking is not required: new files must validate
before their first commit.

This component performs structural validation. DEV-003 extends it under ADR-003:
Git diff supplies changed paths, and the union of PR-declared tasks' implementation
paths must cover every non-excluded path. Only the base commit's canonical policy
can grant exempt/generated status. T2-triggered paths require a covering T2 task.
Each declared T1/T2 task retains its own commit marker, changed-path match, and
risk attestation. Human classification review remains mandatory where required.

DEV-004 makes QG-004 executable under ADR-004. The gate's canonical scope and
implementation_evidence settings determine applicable levels, commit markers,
and changed-path obligations. Validate both base and proposed declarations and
enforce both; other governance families retain their existing behavior.

DEV-005 supplies the reproducible execution environment under ADR-005:
`.python-version` selects the interpreter and `requirements-dev.txt` pins all
validation runtime packages. Local development and CI create a standard isolated
venv, install those pins, verify the environment, then run the unchanged validation
contract. The environment check does not introduce or alter an SDF quality gate.

DEV-014 binds QG-001 (artifact-schema) and QG-002 (reference-integrity) to their
existing, unchanged `scan_artifacts`/`validate_traceability` enforcement paths via
`load_structural_gates`, applying the ADR-004 base/proposed self-protection pattern.
It validates only declaration identity and shape; it never reimplements the schema
or reference engines it binds to.

DEV-015 makes QG-003 (traceability-policy) and QG-005 (risk-attestation) equally
authoritative under ADR-010, via `load_traceability_and_risk_gates`:

- `constitution/policies.yaml` remains the sole operative authority for
  `traceability` and `risk_attestation`; `constitution/quality-gates.yaml`
  declares which policy each gate binds. Two focused JSON Schemas —
  `knowledge/schemas/traceability-policy-gate.schema.json` and
  `knowledge/schemas/risk-attestation-gate.schema.json` — validate contract shape
  only and never define operational policy values.
- QG-003 and QG-005 retain separate gate identities; QG-003 carries no
  independent level list, since trace levels remain canonical only in
  `traceability.levels`.
- `traceability.levels.<level>.requires.risk_attestation` is the sole
  deterministic risk-attestation applicability authority. QG-005 level contracts
  (`required_substrings`) determine evidence content only; an applicable level
  must select a non-empty contract, and a non-applicable level may carry a
  dormant populated contract. No hard-coded `if level in {"T1","T2"}` logic
  remains.
- Base and proposed governance (gate + policy + schema) are each read from their
  own revision and enforced independently by `validate_change_evidence`: for an
  existing task, base obligations use the historical base level applied to the
  surviving proposed evidence, never the historical base evidence; for a task
  new to the proposed graph, its real proposed level is the lookup key in both
  revisions, so a proposed weakening cannot exempt the task that introduces it;
  a base task that remains PR-relevant but absent from proposed traceability
  fails closed, with no successor/lifecycle inference. This is the same
  base-is-a-lower-bound pattern DEV-004/ADR-004 established for QG-004.
- A migration-only compatibility adapter is pinned to the exact pre-Increment-B
  base authorized by Owner Gate B-A. It requires QG-003 and QG-005 to exist
  exactly once in their exact legacy four-field shape at that one revision before
  any normalization occurs, never synthesizes a missing gate, and never consults
  a proposed schema or proposed risk policy to interpret the legacy base;
  every other base and the workspace require the Increment B schemas.
- QG-001, QG-002, QG-004, FR-003/ADR-003 change-provenance behavior, and
  implementation-path resolution are unchanged. QG-006 accountable human review
  and Increment C remain outside this component's Increment B scope; human
  semantic-risk and level-classification judgment remains human-owned, and no
  generic gate/policy engine is introduced.
