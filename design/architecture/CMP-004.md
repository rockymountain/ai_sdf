# Responsibility

CMP-004 narrows the existing CMP-003 controlled-runtime boundary so every fresh
nonimplementation invocation durably proves the structured human authorization
that permitted it. It does not create another runtime or alter implementation
attempt, continuation, circuit, watchdog, or capability semantics.

The governed flow is:

```text
trusted operator/workflow
  -> construct canonical HumanAuthorization
  -> ControlledAIInvocation
  -> gateway/store start transaction
       -> validate invocation and authorization
       -> persist invocation start
       -> append invocation-linked nonimplementation_authorized evidence
       -> commit
  -> read-only AIRuntimePort start
```

`acceptance_validation`, `review`, and `orchestration` always require
`HumanAuthorization`, regardless of whether their scope is new, implicit,
registered, `ACTIVE`, or `STOPPED`. `implementation` retains reservation semantics.
`continuation` retains its existing consumed-attempt lineage and authorization
semantics; CMP-004 neither duplicates nor weakens that path.

# Durable evidence

The authoritative representation is exactly one `execution_evidence` row with:

```text
kind: nonimplementation_authorized
execution_scope_id: invocation.execution_scope_id
invocation_id: invocation.invocation_id
reservation_id: null
payload:
  actor: <HumanAuthorization.actor>
  timestamp: <HumanAuthorization.timestamp>
  reason: <HumanAuthorization.reason>
  disposition: <HumanAuthorization.disposition>
```

The payload is produced from the validated canonical structure, never from prompt
text, provider metadata, logs, environment state, or an untyped CLI flag. The
invocation purpose in the linked invocation row determines whether this evidence is
mandatory. Deterministic verification answers the authorization question by joining
the invocation to this evidence and requiring exactly one valid row for each in-scope
purpose.

No schema change is required. `execution_evidence` is already the generic,
invocation-linkable, restart-safe evidence mechanism. A new governed `kind` value
adds evidence semantics without adding or reinterpreting a table or column.

# Atomicity and lifecycle

Authorization validation, invocation-start persistence, and authorization-evidence
persistence occur in the same database transaction. The transaction commits before
`AIRuntimePort.start` may be called. Missing or malformed authorization, evidence
insertion failure, or transaction failure rolls back the whole start and prevents
the provider call.

The authorization event records permission for the invocation, not proof that the
provider executed it. Therefore it remains truthful when later start evidence proves
definite non-start, uncertain start, or accepted start. Terminal failure and timeout
do not rewrite it. Existing start and terminal evidence continue to describe what
the runtime did. A restart can reconstruct the authorization from the retained event.

Duplicate or replayed `invocation_id` values fail through the existing invocation
identity constraint. Verification treats zero or multiple authoritative
authorization events for one required invocation as invalid evidence.

For a `STOPPED` scope, existing `non_mutating_disposition` evidence continues to
record the circuit disposition. It is not the authoritative invocation-authorization
record and does not replace `nonimplementation_authorized`.

# Capability and attempt separation

All three in-scope purposes remain read-only and cannot acquire repository/workspace
implementation mutation capability from operator input. They reserve or consume no
implementation capacity, create no attempt, reopen no attempt, and create no
checkpoint result. Their invocation and usage evidence remain attributable to the
declared DEV task.

# Compatibility

Historical DEV-007, schema-v2, and existing schema-v3 rows remain historical facts.
Missing authorization events are not synthesized or backfilled. The strengthened
rule applies prospectively to starts governed by the implementation of this design.
Existing `live-proof` behavior remains available until the implementation adds the
required structured operator input; historical proof evidence is not reinterpreted.

Existing continuation authorization in `invocation_attempts.human_authorization`
and `continuation_authorized` evidence remains authoritative for continuation.
Schema migration behavior and schema version 3 remain unchanged.

# Rejected alternatives

- Process-local authorization is not restart-safe and disappears after execution.
- Prompt or prose authorization is unstructured, non-authoritative, and not safely
  queryable.
- `invocation_attempts.human_authorization` is attempt-lineage evidence and would
  falsely associate nonimplementation work with implementation attempts.
- `execution_scopes.authorization` describes successor-scope authority, not the
  authorization of each invocation, and cannot represent multiple invocations.
- Adding authorization to `invocations` would require an unnecessary schema change
  and would conflate invocation telemetry with generic governance evidence.

# Boundaries

CMP-004 does not authorize implementation, provider execution, operational database
migration, an M3 measurement window, M4, automatic routing, Graphify, or unrelated
CLI refactoring. Operator tooling remains orchestration; runtime policy and evidence
semantics remain authoritative in the controlled-runtime modules.
