# Context

`ControlledAIInvocation` carries structured `HumanAuthorization`, but the current
fresh or active-scope path for `acceptance_validation`, `review`, and
`orchestration` neither requires nor durably records it. Continuation authorization
is durable, and stopped-scope non-mutating disposition is recorded, but neither is a
general authorization record for these purposes. Operator adoption would therefore
allow required authorization to disappear after process exit.

# Decision

1. Every `acceptance_validation`, `review`, and `orchestration` invocation requires
   a valid canonical `HumanAuthorization`. This applies to implicit compatibility
   scopes and registered scopes in both `ACTIVE` and `STOPPED` states.
2. The exact `actor`, timezone-qualified `timestamp`, `reason`, and `disposition`
   fields are stored as one invocation-linked `execution_evidence` event with kind
   `nonimplementation_authorized` and no reservation identity.
3. Validation, invocation-start insertion, and authorization-event insertion are
   one transaction. The transaction must commit before the runtime port is called.
4. No schema change or schema-version increment is required. The existing generic
   `execution_evidence` mechanism is used.
5. The event proves authorization was granted for the invocation; it does not claim
   the runtime started. Definite non-start, uncertain start, accepted start, timeout,
   and terminal failure retain their existing independent evidence semantics.
6. Missing/malformed authorization or failure to persist it prevents runtime start.
   Replay of an invocation identity remains rejected. Zero or multiple authoritative
   events makes deterministic authorization verification fail closed.
7. Operator tooling must accept all canonical authorization fields explicitly,
   construct the existing structured type, and pass it to the controlled runtime.
   A boolean flag or prompt prose is insufficient.
8. Existing nonimplementation purposes remain read-only and outside implementation
   attempt capacity. Continuation and implementation semantics remain unchanged.

# Query contract

For invocation `X`, deterministic verification reads its purpose and joins
`execution_evidence` on `invocation_id=X` and
`kind='nonimplementation_authorized'`. For an in-scope purpose, exactly one row must
exist and its parsed payload must contain exactly the validated canonical fields.
Because insertion shares the invocation-start transaction and commits before the
port call, that row proves durable authorization preceded permitted execution.

# Historical compatibility

The rule is prospective. Existing DEV-007 and schema-v2/v3 rows are not backfilled
or treated as newly verified. Existing continuation and stopped-scope disposition
evidence keeps its historical meaning. `live-proof` must remain behaviorally
available, but future use after implementation must supply structured authorization.

# Alternatives considered

- **Process-local authorization only:** rejected because it is not durable.
- **Prompt/prose authorization:** rejected because it is not governed structured
  evidence and cannot be deterministically queried.
- **Reuse `invocation_attempts`:** rejected because nonimplementation work has no
  attempt identity and must not create one.
- **Use `execution_scopes.authorization`:** rejected because scope authorization is
  not per-invocation and currently represents successor authority.
- **Use generic `execution_evidence`:** selected because it is durable, linked to
  invocation and scope, transactional, queryable, and semantically generic.
- **Add authorization to `invocations`:** rejected because it requires an
  unnecessary schema migration and couples governance evidence to telemetry layout.

# Consequences

Implementation changes authorization validation and persistence behavior in the
controlled start transaction and exposes structured operator inputs. Deterministic
tests must prove fail-closed atomicity, restart queryability, capability separation,
and regressions. Project Owner approval authorizes DEV-012 implementation but not
the separately gated live provider adoption proof.
