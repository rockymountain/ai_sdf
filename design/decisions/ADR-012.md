# Context

CMP-003 already isolates provider-specific execution behind `AIRuntimePort`, and
ADR-008 separates provider-neutral measurement validation from concrete treatment
selection. The pre-window execution strategy now needs Claude as a controlled
implementation executor and Codex as an independent read-only auditor without
creating separate safety, attribution, or acceptance systems. The current flat
`MeasurementWindow` treatment cannot truthfully describe two valid runtimes in one
DEV.

# Decision

1. Preserve the existing hard boundary:

   ```text
   ControlledAIInvocation Gateway -> AIRuntimePort -> replaceable runtime adapter
   ```

   `AIRuntimePort`, attempt, reservation, circuit, watchdog, continuation, and
   acceptance semantics do not change.
2. Keep `invocation_purpose` as the sole canonical execution role. Do not add an
   agent-role or runtime-role registry.
3. Runtime adapter selection is explicit trusted-workflow configuration. The
   operator supports the identifiers `codex` and `claude`; Codex remains the
   backward-compatible default and no automatic routing is introduced.
4. Adapter choice cannot grant capability. The gateway continues to derive
   capability from invocation purpose and attempt lineage. Implementation and valid
   continuation may be mutation-capable; review, acceptance-validation, and
   orchestration remain read-only.
5. A measurement window declares a non-empty `purpose_treatments` mapping. Every
   entry explicitly supplies:

   ```yaml
   runtime_adapter:
   requested_model:
   requested_reasoning_effort:
   model_selection_strategy:
   routing_policy_version:
   context_strategy:
   ```

   No purpose silently inherits another purpose's treatment.
6. Treatment consistency compares the retained invocation's authoritative
   `adapter_name` and requested profile with the entry for its invocation purpose.
   Missing adapter identity is not inferred from model identity. Undeclared purposes
   and mismatches retain cost but make exact treatment-dependent KPIs unavailable.
7. DEV reports retain the total across all purposes and add deterministic usage
   breakdowns by purpose and runtime adapter. Unknown contributions remain unknown
   while exact known subtotals remain visible. The derived report schema advances
   from version 1 to version 2 for this changed declaration/report shape; the
   operational telemetry schema remains version 3 and is not migrated.
8. Exact canonical usage requires authoritative machine-readable provider components
   sufficient to determine canonical input and output token counts without estimation.
   Canonical `total_tokens` is deterministically derived as canonical input plus
   canonical output when both components are exact. An adapter may consume
   provider-specific authoritative components to derive those canonical fields;
   missing required provider components remain unknown. Provider-specific formulas
   do not enter generic policy or `MeasurementWindow` declarations.
9. The accepted Claude adapter uses the supported noninteractive Claude Code CLI
   stream-JSON surface. It maps an assistant event or successful result to accepted
   start; process creation failure before a process exists to definite non-start;
   and a process that ends without affirmative acceptance to uncertain start. It
   normalizes exact emitted base input, cache-creation input, cache-read input, and
   output components into canonical input/output/derived-total evidence. All required
   components must be non-negative integers. Cache read alone maps to the generic
   `cached_input_tokens` breakdown; cache creation remains provider-native evidence.
   Safe emitted usage key names and numeric values are retained in native metadata,
   while prompt/response content and missing or synthetic values are not. Otherwise
   usage is unknown. Provider/session identifiers are recorded only when emitted.
10. The adapter enforces implementation capability with Claude's mutation-capable
   `acceptEdits` mode. File edits and supported filesystem operations may proceed
   without prompts; other operations may remain denied or prompt-gated. Read-only
   capability uses plan mode, the built-in `Read`, `Glob`, and `Grep` tools, and
   strict MCP configuration with no supplied MCP servers. The subprocess working
   directory is the governed repository. The adapter does not depend on VS Code
   conversation state, scrape UI, create an autonomous tool loop, or enable
   unrestricted permission bypass.
11. The concrete Claude model used by a future window is declaration data. No
    provider/model assignment becomes a generic factory invariant.
12. Operator input uses the explicit literal `none` to represent canonical null
    requested reasoning effort. Other non-empty values remain explicit capability
    requests; the operator supplies no default and the adapter omits `--effort` for
    null.

# Historical compatibility

No canonical or persisted measurement-window declaration exists, and the actual M3
window has not started. The contract therefore evolves directly from the flat source
shape to `purpose_treatments`; no hypothetical legacy declaration reader is added.
DEV-011 and DEV-013 remain truthful historical implementation evidence, and no
telemetry or report is rewritten.

# Consequences

One governed DEV can use Claude implementation plus Codex review while retaining
normal safety, budget, telemetry, and acceptance behavior. The change adds one
adapter and a small explicit operator resolver, not a multi-agent framework,
provider marketplace, general plugin system, or automatic router.
