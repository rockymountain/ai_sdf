# Context

Phase 0 established canonical traceability, deterministic gates, reproducible
validation, and human accountability. It did not implement an autonomous AI runtime.
Phase-1 discovery established invocation control, streamed evidence, interruption,
and exact usage for a completed no-tool bootstrap invocation while provider-internal
requests may remain opaque. Tool-bearing current-invocation completeness remains a
DEV-007 acceptance proof.

Phase 1 requires cost attribution and a hard two-attempt circuit before bounded
autonomy can be enabled. Canonical execution policy and evidence must survive process
restart, prevent concurrent budget races, distinguish requested from observed
execution identity, retain unknown usage honestly, and remain portable across
replaceable AI runtimes.

# Decision

## 1. Canonical controlled invocation boundary

Define `ControlledAIInvocation` as one SDF-authorized execution unit exposed by an
AI runtime adapter. Define `ProviderRequest` as an optional opaque request issued
internally by a runtime or provider; it is not a mandatory Phase-1.0 accounting or
enforcement unit.

Use CMP-003 as the boundary:

```text
SDF workflow
  -> Execution Scope / Budget Guard
  -> ControlledAIInvocation Gateway
  -> AIRuntimePort
  -> replaceable runtime adapter
  -> opaque 0..N ProviderRequest
```

The hard enforcement point is immediately before `AIRuntimePort` starts a
`ControlledAIInvocation`. Every controlled invocation must pass through the guard
and gateway before the port is called.

The SDF-owned `AIRuntimePort` concept provides three capabilities:

- start or invoke one authorized controlled invocation;
- stream or otherwise observe invocation evidence;
- interrupt an active invocation.

This section ratifies Phase-1 invariant P1-I15. Canonical SDF execution policy,
attempt accounting, circuit state, telemetry schema, and acceptance logic must not
depend on runtime-provider SDK domain types. Runtime-specific semantics are isolated
inside a replaceable adapter. The port is a narrow execution boundary, not a
universal provider framework or router.

## 2. Bootstrap adapter mapping

The Phase-1.0 bootstrap implementation is `CodexRuntimeAdapter`, which maps the
provider-neutral port to the public OpenAI Codex Python SDK:

```text
runtime_session_id       <- Codex thread_id
runtime_invocation_id    <- Codex turn_id
start invocation         -> thread.turn(...)
stream evidence          -> TurnHandle.stream()
interrupt invocation     -> TurnHandle.interrupt()
current UsageEvidence    <- ThreadTokenUsage.last
cumulative reconciliation evidence
                          <- ThreadTokenUsage.total
```

For this adapter, the hard boundary maps to immediately before `thread.turn(...)`.
`thread.run()` may be used only where the adapter preserves the same evidence and
interruption contract; it must not discard usage observed before a failed or
interrupted terminal status.

Human-driven Codex sessions outside the controlled flow are not claimed as
autonomous Phase-1 execution and are not silently included in its measurements.
Provider-internal request count and identity may remain opaque.

## 3. Runtime-adapter conformance

Every `AIRuntimePort` adapter must pass conformance tests that prove:

1. an invocation blocked by the SDF guard does not reach the runtime;
2. an authorized invocation has finite watchdog and interruption support;
3. SDF `invocation_id` correlates with provider-neutral runtime session and
   invocation identities when the runtime exposes them, and their absence remains
   explicit;
4. usage is mapped to exact `UsageEvidence` or explicitly to
   `usage_status=unknown`;
5. runtime terminal outcomes map to the SDF terminal outcome vocabulary;
6. affirmative accepted-execution, affirmative non-start, and insufficient evidence
   map to `CONSUMED`, `RELEASED`, and `UNRESOLVED` respectively;
7. no adapter path or invocation purpose bypasses SDF attempt or circuit governance.

Adding a second runtime requires a new adapter and these conformance tests. It does
not require redesigning attempt, circuit, telemetry, or acceptance policy. Phase 1.0
does not perform automatic provider routing.

## 4. Identity and attribution

Every `ControlledAIInvocation` has these mandatory SDF-owned identities before
runtime start:

- `dev_task` and `traceability_level` identify governed intent;
- `execution_scope_id` is the stable governed execution-objective identity. It owns
  implementation-attempt budget when implementation applies; non-implementation
  invocations use it for attribution, provenance, lifecycle, and circuit enforcement
  without creating attempt capacity;
- `run_id` identifies one runtime process or workflow run without owning budget;
- `invocation_id` is the SDF-owned identity of one `ControlledAIInvocation`;
- `source_revision` identifies the canonical Git base revision associated with the
  governed execution objective and invocation. It does not assert a clean working
  tree, absence of partial edits, or a complete snapshot of invocation input.

An implementation invocation that reserves attempt capacity also has:

- `reservation_id`, the SDF-owned identity of one attempt-slot reservation
  transaction;
- `candidate_attempt_number`, the slot claimed while the reservation is active.

Reservation does not create `attempt_number`. Only `RESERVED -> CONSUMED` binds
`candidate_attempt_number` as `attempt_number`, the ordinal of the consumed
implementation attempt. Review or orchestration invocations may have neither
`reservation_id` nor `attempt_number` when they are outside an implementation
attempt.

Every invocation declares one provider-neutral `invocation_purpose`:

- `implementation` requires attempt-capacity reservation;
- `continuation` requires an existing consumed attempt and P1-I16 lineage;
- `acceptance_validation` requires explicit human authorization, may omit
  reservation and attempt identity, performs no autonomous implementation work, and
  creates or replenishes no attempt budget;
- `review` and `orchestration` may omit implementation reservation and attempt
  identity.

All purposes retain the mandatory SDF identities above. DEV-007's live tool-bearing
proof is classified `acceptance_validation`. Purpose classification is not an
attempt-governance bypass.

Any controlled invocation that omits implementation-attempt identity must be denied
repository/workspace implementation mutation capability. Mutation requires
`invocation_purpose=implementation` with reservation identity or
`invocation_purpose=continuation` with P1-I16 consumed-attempt lineage.
`acceptance_validation`, review, and orchestration are non-mutating when they omit
attempt identity. An adapter may use a read-only sandbox or equivalent restriction;
the canonical design does not prescribe a provider SDK mechanism, and purpose
classification alone is insufficient enforcement.

`runtime_session_id`, `runtime_invocation_id`, and `runtime_native_metadata` are
optional correlation evidence. They are persisted only when the adapter or runtime
actually exposes them. Their absence is explicit and does not affect SDF attempt or
circuit correctness. An adapter must not invent native, session, or invocation
identifiers solely to satisfy telemetry.

`invocation_id` and its start record are persisted before runtime spend. Optional
runtime correlation evidence is attached when observed. Neither native metadata nor
runtime IDs become policy authority.

A P1-I16 continuation may retain the same `source_revision` while resuming partial
workspace changes. Phase 1.0 introduces no workspace fingerprint, checkpoint, or
exact workspace-replay subsystem; such capability requires later governed need.

A new run, runtime session, adapter process, or provider-native session for the same
objective reuses the existing `execution_scope_id` and therefore cannot reset budget.

## 5. Attempt and acceptance semantics

An attempt is one autonomous implementation plus deterministic test or validation
cycle for the same execution scope. A successful runtime invocation is not an
attempt success.

Every reservation receives a unique `reservation_id` and exclusively claims a
`candidate_attempt_number` for its scope. Reservation does not by itself create an
`attempt_number` or consume an implementation-attempt budget slot. Concurrent
processes cannot hold the same active candidate slot.

The reservation state changes as follows:

- `RESERVED -> CONSUMED` only on affirmative evidence that the runtime or provider
  accepted execution. The reservation then binds its
  `candidate_attempt_number` as the
  consumed `attempt_number`;
- `RESERVED -> RELEASED` only on affirmative evidence that runtime execution
  definitely did not start. Failure evidence is retained and the
  implementation-attempt budget is not consumed. The durable released record keeps
  its `reservation_id` but no longer occupies the candidate slot;
- `RESERVED -> UNRESOLVED` when evidence is insufficient to establish either
  accepted execution or definite non-start. The reservation remains unavailable,
  autonomous continuation stops, and human resolution is required.

From `UNRESOLVED`, later affirmative non-start evidence permits `RELEASED`, later
affirmative accepted-execution evidence requires `CONSUMED`, and insufficient
evidence leaves it `UNRESOLVED`. Each runtime adapter defines its concrete evidence
mapping in its conformance specification; the canonical core remains provider-neutral.

If evidence remains permanently insufficient, the reservation stays immutable and
`UNRESOLVED`, its scope stays stopped, and no reservation or budget capacity is
released or restored. Further work on the objective requires a human-authorized
successor `execution_scope_id` recording predecessor scope, actor, timestamp, reason,
and disposition. A fresh unlinked scope is an anti-bypass violation.

After `RELEASED`, a later transaction may claim the same next candidate number with
a new `reservation_id`. Released evidence is never deleted or overwritten to make
the slot reusable. Consumed attempts are unique by
`execution_scope_id + attempt_number`.

The deterministic acceptance checkpoint is the only event that closes a `CONSUMED`
attempt as successful or failed. An invocation failure, timeout, interruption, or
unknown usage after actual or potentially actual spend cannot create a free retry.

Reservation lifecycle and consumed-attempt lifecycle are separate. A consumed
attempt starts `OPEN`. Deterministic acceptance closes it as `PASSED` or `FAILED`.
An already-consumed attempt may become `SUSPENDED` only for a governed resumable
interruption, and uncertain terminal evidence enters `RECONCILIATION_REQUIRED`
rather than silently becoming resumable.

Phase 1.0 recognizes only affirmative `terminal_status=interrupted` with
`terminal_reason=usage_limit` as resumable. Every continuation requires explicit
recorded human authorization, a new `invocation_id`,
`resume_of_invocation_id`, the same `execution_scope_id`, the same consumed
`attempt_number`, an unchanged implementation objective, and an unclosed
deterministic checkpoint. The continuation returns `SUSPENDED -> OPEN`; it does not
create an attempt, replenish budget, or decide attempt success. Watchdog timeout,
runtime failure, network error, cancellation, and unknown terminal state are not
automatically resumable. A deterministic implementation or test failure cannot be
relabeled as continuation.

`RECONCILIATION_REQUIRED` has only these legal resolutions:

- recovered affirmative `interrupted/usage_limit` evidence moves the attempt to
  `SUSPENDED`, after which a human may authorize continuation;
- recovered deterministic checkpoint evidence moves it to `PASSED` or `FAILED`
  according to that checkpoint;
- otherwise, record human disposition, keep the scope stopped, and require a
  human-authorized successor scope for further work.

Human resolution cannot manufacture deterministic PASS/FAIL, free consumed budget,
or create a retry.

Review and orchestration invocations are attributed to the DEV task and scope but do
not automatically reserve an implementation attempt. Phase 1.0 does not enable an
autonomous reviewer. The golden path uses one primary controlled implementation
invocation followed by deterministic validation; governed continuation invocations
may remain within that same consumed attempt.

## 6. Canonical budget authority

`constitution/policies.yaml` is the single executable canonical authority for the
`autonomous_execution` namespace. The delivery sequence is:

- DEV-007 introduces `autonomous_execution.max_invocation_seconds` and its
  fail-closed reader. The schema requires a positive integer, and its numeric value
  must be human-approved before the live controlled-invocation acceptance test;
- DEV-008 introduces and validates:

```yaml
autonomous_execution:
  max_attempts: 2
```

This proposed ADR does not edit governance or choose
`autonomous_execution.max_invocation_seconds`. Each batch reads its canonical
policy directly and fails closed when the required value is absent, malformed,
unreadable, or unsupported. There is no permissive default and no duplicate
authority in code, prompts, `.codex/config.toml`, provider settings, adapter
metadata, or generated `AGENTS.md`.

## 7. Circuit and atomicity

This section ratifies Phase-1 invariant P1-I13.

For one `execution_scope_id`, candidate-slot reservation, remaining-budget
evaluation, reservation-state transitions, consumed-attempt binding, and transition
to `CIRCUIT_OPEN` are atomic.

Local SQLite at `.sdf/runtime/ai-execution.sqlite3` is the Phase-1 operational
evidence store. The `.sdf/runtime/` tree is local state and must be excluded from
Git. Each durable reservation record has a unique `reservation_id`. The logical
state machine guarantees one active candidate slot per scope and uniqueness of
consumed `execution_scope_id + attempt_number`. A proven pre-start failure releases
the active claim transactionally while retaining the reservation and failure
evidence. A later reservation may reuse that candidate number with a new
`reservation_id`. An uncertain start keeps the claim unavailable as unresolved.
Process-local locks may reduce contention but are not correctness authority.

This ADR intentionally does not prescribe a physical SQLite index or table layout;
the implementation may use transactional, state-machine, or conditional uniqueness
mechanisms that preserve these logical invariants and audit history.

This section also ratifies P1-I17. For one scope, at most one implementation
attempt may be open. A new reservation is rejected while the scope contains an
active `RESERVED` reservation, an `UNRESOLVED` reservation, or a consumed attempt
not yet closed by deterministic acceptance. A passed attempt accepts the scope and
permits no next attempt. Only a failed closed attempt with remaining budget permits
the next reservation. Durable state and transactional exclusion make this rule
survive restart and concurrent processes without prescribing physical SQLite
indexes.

When the deterministic acceptance checkpoint fails consumed attempt 2, one
transaction:

1. records the failed checkpoint and evidence;
2. marks attempt 2 failed;
3. transitions the scope to `CIRCUIT_OPEN`;
4. commits before another invocation can be authorized.

The gateway checks durable scope state immediately before every `AIRuntimePort`
start. Once the circuit is open, every later controlled invocation for that scope is
rejected locally and returns `human_attention_required`; no candidate attempt 3 can
be consumed and no controlled invocation belonging to implementation attempt 3
reaches `AIRuntimePort`. Governed continuation invocations within an already
consumed open attempt do not increment `max_attempts`, so raw invocation count is
never used as an attempt-count proxy. Opaque provider requests inside an invocation
authorized before its terminal outcome remain part of that invocation and are not a
post-circuit bypass.

## 8. Watchdog and unresolved state

This section ratifies Phase-1 invariant P1-I14.

Every controlled invocation has a finite watchdog persisted before the runtime port
is invoked. The watchdog enforces the canonical
`autonomous_execution.max_invocation_seconds` policy. Its schema requires a positive
integer. The mechanism, canonical policy/read, and fail-closed behavior belong to
DEV-007 because its acceptance test performs a real controlled invocation. A
human-approved value is required before that test; this ADR does not choose it. On
expiry the controller asks `AIRuntimePort` to interrupt the invocation, records
`terminal_status=timeout` and terminal evidence, retains exact usage already
observed, or records `usage_status=unknown`, never zero, and requires human attention.
If the invocation belongs to a consumed implementation attempt, that attempt enters
`RECONCILIATION_REQUIRED`. If it has no consumed attempt, no attempt-state transition
occurs and no attempt or budget capacity is invented; autonomous follow-on in that
scope stops pending governed human disposition. A later explicitly human-authorized
non-mutating validation or review action must follow that disposition and cannot
create implementation capacity. A timeout is not automatically resumable or an
uncounted retry. This is distinct from reservation `UNRESOLVED`, where evidence
establishes neither accepted execution nor definite non-start.

Failed and interrupted invocations may lack exact usage. Unknown is an evidence
state, not a token value. An invocation with unknown usage remains attributable to
DEV, scope, run, consumed attempt when applicable, runtime correlation IDs when
available, timestamps, and terminal outcome.

## 9. Telemetry contract

Persist at least:

- attribution: DEV task and traceability level;
- execution: mandatory scope, run, SDF invocation, source revision,
  `reservation_id` and `candidate_attempt_number` when reserving implementation
  work, consumed `attempt_number` when applicable, and `invocation_purpose`; optional
  runtime session, runtime invocation, and native metadata;
- runtime: adapter name/version and runtime name/version;
- requested profile: model and capability-aware reasoning effort when requested and
  supported, `model_selection_strategy`, and optional `routing_policy_version`;
- observed profile: observed model only when affirmatively evidenced, plus reroute
  event/reason/from/to when actually observed;
- treatment: machine-readable `context_strategy` using `chat-heavy`,
  `manual-context-pack`, `graphify-context-pack`, or `other`;
- usage: core input, output, and total tokens; optional cached-input and
  reasoning-output breakdowns; and `usage_status=exact|unknown`;
- lifecycle: `terminal_status`, optional `terminal_reason`, optional
  `resume_of_invocation_id`, and recorded continuation authorization;
- timing and terminal outcome;
- final DEV acceptance outcome when known.

`UsageEvidence` is provider-neutral. Exact core usage means the adapter supplied
machine-readable `input_tokens`, `output_tokens`, and `total_tokens` attributable to
the current controlled invocation. `cached_input_tokens` and
`reasoning_output_tokens` are optional breakdowns: unsupported absence is explicit,
never zero, and does not make otherwise exact core usage unknown.
`CodexRuntimeAdapter` records both because Codex exposes them. Unknown means the core
evidence was unavailable or unusable; token fields are absent rather than zero.
Requested model and reasoning values are never proof of observed execution identity,
and reasoning effort is not invented for runtimes without that capability. Absence
of a reroute event is not proof that requested and observed models are equal.
Runtime-native metadata is evidence only and cannot amend policy.

`context_strategy` is measurement metadata only. Phase 1.0 does not implement
Graphify, Context Pack routing, or automatic context optimization.

`model_selection_strategy` is `fixed`, `manual`, `risk_routed`, or `other`.
`routing_policy_version` may be absent when routing is inactive and must identify the
governed policy if risk-routed or automatic routing is later enabled. Phase 1.0 does
not enable automatic model routing; both fields exist for measurement readiness and
Phase-1.1 experiment comparability.

`terminal_status` and `usage_status` are independent. Provider-neutral terminal
statuses are `success`, `failure`, `interrupted`, `timeout`, `cancelled`, and
`unknown`. Terminal reasons may be `usage_limit`, `watchdog_timeout`,
`runtime_error`, `user_cancelled`, `other`, or `unknown`. Only affirmative
`terminal_status=interrupted` plus `terminal_reason=usage_limit` is governed as
resumable in Phase 1.0.

Attempt, DEV, and experiment/window aggregates record
`usage_completeness=complete|incomplete`. Completeness is `complete` only when every
contributing controlled invocation has exact usage. If any contribution is unknown,
known token values remain a `known_subtotal`, completeness is `incomplete`, and the
subtotal must not be presented as an exact aggregate total. Unknown is never
invented as zero.

Unknown usage normally stops autonomy. The sole exception is a human-authorized
P1-I16 continuation backed by affirmative `interrupted/usage_limit` terminal
evidence. Previous unknown usage remains unknown unless machine-readable evidence is
later recovered; continuation does not require it to become exact, and all enclosing
aggregates remain incomplete unless every contributing invocation later becomes
exact.

Measurement coverage reports usage-complete accepted DEV divided by all accepted
DEV. An incomplete DEV or window may be reported operationally but cannot be
silently excluded from an exact KPI. Phase-1.1 exact token KPIs and the context
treatment gate are decision-eligible only when every contributing accepted DEV has
complete usage. Otherwise report incomplete coverage and known subtotals without an
exact reduction claim. Any statistical or imputation treatment requires separate
governed approval; zero is never imputed.

For `CodexRuntimeAdapter`, `ThreadTokenUsage.last` maps to current-invocation
`UsageEvidence`. `ThreadTokenUsage.total` is retained only as cumulative runtime
session reconciliation evidence and must not be summed across invocations.

Before DEV-007 claims complete telemetry coverage, TEST-007 must exercise a
successful Codex SDK turn containing a real command or tool item and demonstrate
that `ThreadTokenUsage.last` covers the full current turn while
`ThreadTokenUsage.total` is cumulative for the thread. The invocation is explicitly
human-authorized `acceptance_validation`, uses a non-mutating capability profile,
and proves governed repository/workspace state was not mutated. A read-only sandbox
is one permitted adapter mechanism, not a canonical dependency. TEST-007 also proves
that watchdog timeout of this non-attempt invocation records terminal and usage
evidence, requires human attention, stops autonomous follow-on, and creates no fake
consumed attempt or budget capacity.

Do not store raw prompts or responses solely for accounting. Content needed for a
separate governed diagnostic purpose requires its own classification and retention
decision.

## 10. Persistence and authority separation

Canonical Git stores policy and design. Local SQLite stores observed operational
evidence and durable circuit state. Experiment reports are derived outputs rebuilt
from canonical definitions plus retained observations.

Operational evidence cannot amend policy or design. Telemetry loss cannot be repaired
by inventing values. Before data is collected, DEV-007 must implement and verify
storage permissions, schema and version handling, Git exclusion, a declared
retention policy, and reproducible query or export for experiment evidence. Circuit
and attempt records must survive process restart, and experiment results must remain
reproducible from retained observations for the declared measurement window.

Phase-1.0 retains observations for the complete declared measurement window and
until the associated experiment report is accepted and its reproducibility check
passes. Later deletion requires a recorded disposition linked to the affected
measurement window; there is no automatic time-based deletion in Phase 1.0.

A remote or off-device backup subsystem is deferred unless later risk evidence or
measurement-window durability demonstrates a need.

## 11. Delivery sequencing

DEV-007 provides `AIRuntimePort`, `CodexRuntimeAdapter`, telemetry, the finite
watchdog mechanism and canonical `max_invocation_seconds` policy/read,
exact-or-unknown evidence, and the tool-bearing live acceptance proof. That live
test is explicitly human-authorized `acceptance_validation`; it omits attempt
identity, performs no autonomous implementation work, and creates no budget.
DEV-007 does not enable
autonomous multi-attempt retry. DEV-008 then provides canonical `max_attempts=2`,
the attempt controller, reservation and consumed-attempt lifecycles, one-open-attempt
enforcement, circuit breaker, and successor-scope anti-bypass behavior. Only after
DEV-008 may bounded autonomous retry be enabled.

The positive-integer `max_invocation_seconds` value must be human-approved before
DEV-007's live acceptance test. Both policies reside in the single canonical
`autonomous_execution` namespace in `constitution/policies.yaml`, but this
design-only ADR does not modify executable governance.

## 12. Human-authorized continuation

P1-I16 permits continuation inside an already-consumed, unclosed attempt only after
the governed resumable external condition `usage_limit` and explicit human authorization. The successor
controlled invocation records a new `invocation_id`,
`resume_of_invocation_id`, the same scope and attempt, and unchanged objective. The
attempt remains `SUSPENDED` until authorized continuation returns it to `OPEN`.
Continuation does not replenish budget, decide acceptance, or authorize automatic
resume. All continuation usage is real AI cost.

Timeout, runtime failure, network error, cancellation, unknown terminal state, and
deterministic implementation or test failure are not automatically resumable.

Phase 1.0 does not replenish an existing scope's attempt budget. After
`CIRCUIT_OPEN`, continuation requires a human-authorized new `execution_scope_id`
linked to the predecessor with actor, timestamp, reason, and disposition. The closed
scope, attempts, invocation evidence, and cost remain immutable. Creating a new run,
runtime session, adapter process, or provider-native session without this
authorization remains bound to the old scope and is rejected.

Any future same-scope reset mechanism requires a separate governed decision. It may
not silently delete history or reinterpret prior attempts.

## 13. Lean cost optimization

The optimization objective is to minimize AI resource cost per accepted DEV subject
to deterministic-quality non-regression, governance and security non-regression,
acceptable acceptance rate, bounded retry, and human accountability.

Graph or context treatment and model-tier or reasoning treatment are separate
experiments. Telemetry preserves both dimensions so their effects are not conflated.
Phase 1.0 does not introduce automatic routing. Exact monetary or platform-credit
attribution is optional; exact token accounting remains the model-independent
primary evidence.

The baseline also measures `usage_limit` interruptions per DEV, continuation
invocations per accepted DEV, input tokens in continuation invocations per accepted
DEV, and human continuation actions per DEV. Phase 1.0 does not claim duplicated or
replayed-token waste without supporting instrumentation and does not implement
checkpointing, automatic resume, context compaction, or a continuation manifest.
Those remain possible Phase-1.1 treatments after baseline evidence exists.

## 14. Design-lock Definition of Done

ADR-006 is design-lock ready only when the following answers are deterministic and
testable:

1. `ControlledAIInvocation` is the SDF accounting unit and its hard boundary is the
   guarded start through `AIRuntimePort`.
2. The minimum port contract is start/invoke, observe/stream evidence, and interrupt.
3. Mandatory pre-start identities are DEV task, traceability level, scope, run,
   invocation, and source revision; every invocation declares purpose, and
   implementation reservations additionally carry reservation and candidate-attempt
   identity. Any purpose without implementation-attempt identity is deterministically
   denied implementation mutation capability.
4. `RESERVED -> CONSUMED` alone binds `candidate_attempt_number` to
   `attempt_number`; mutually exclusive adapter evidence selects consumed, released,
   or unresolved, and both unresolved and reconciliation-required states have closed
   legal outcomes that cannot manufacture acceptance or retry.
5. Durable transactional scope state enforces at most one open implementation
   attempt across restart and concurrency.
6. Deterministic acceptance closes an attempt, and failure of consumed attempt 2
   opens the circuit atomically.
7. No candidate attempt 3 can become consumed or reach `AIRuntimePort` after two
   failed consumed attempts.
8. Provider-neutral exact-core/optional-breakdown usage and aggregate
   complete/incomplete semantics preserve known subtotals, disclose accepted-DEV
   coverage, and prevent incomplete windows from producing exact treatment claims.
9. The finite watchdog reads fail-closed from the canonical positive-integer
   `max_invocation_seconds` policy and handles attempt and non-attempt timeouts
   without inventing attempt state.
10. Requested model identity is distinct from affirmatively observed model evidence.
   Model-selection strategy and routing-policy version preserve experiment
   comparability, and machine-readable context strategy preserves context-treatment
   comparability, without enabling Phase-1.0 automatic routing or context optimization.
11. Runtime-specific SDK semantics remain isolated inside replaceable adapters, and
   TEST-007 proves its real tool-bearing acceptance validation cannot mutate governed
   repository/workspace state.
12. Human-authorized `terminal_status=interrupted` and
    `terminal_reason=usage_limit` continuation preserves the same consumed attempt,
    permits prior usage to remain unknown, and cannot bypass attempt accounting.
13. Post-circuit continuation requires a successor scope whose provenance preserves
    immutable closed-scope history.

# Consequences

The SDF can block spend before each controlled invocation, attribute exact or unknown
usage, and prevent post-circuit invocations across restarts and concurrent processes.
Its canonical policy and evidence model depend on `AIRuntimePort`, not on bootstrap
SDK types.

Codex-first does not mean Codex-dependent. `CodexRuntimeAdapter` supplies the initial
mapping, while a second runtime requires a new adapter and conformance tests rather
than redesign of attempt, circuit, telemetry, or acceptance policy.

The design accepts controlled-invocation accounting rather than provider-request
accounting. It also requires a local operational database and explicit reconciliation
of unresolved terminal states. Full telemetry coverage remains unproven until the
tool-bearing bootstrap-adapter acceptance case passes.

# Enablement conditions

Before DEV-007 starts its live controlled-invocation acceptance test:

1. the `autonomous_execution.max_invocation_seconds` field, positive-integer schema,
   and value are human-approved;
2. the watchdog policy reader fails closed and has no fallback;
3. the test invocation is forced through CMP-003 and `AIRuntimePort`.
4. the invocation is explicitly human-authorized as `acceptance_validation` and is
   prohibited from autonomous implementation work.

DEV-007 acceptance then requires the bootstrap adapter to pass its conformance and
tool-bearing telemetry tests and verify exact/unknown terminal handling and
human-attention behavior.

Before DEV-008 enables bounded retry:

1. canonical `max_attempts=2` and its schema are human-approved;
2. SQLite reservation/consumption state, restart persistence, and final-failure
   circuit transition are verified;
3. proven pre-start release and insufficient-evidence unresolved behavior are verified;
4. one-open-attempt exclusion is verified across restart and concurrency;
5. governed same-attempt continuation and its anti-bypass checks are verified;
6. a candidate attempt 3 and its controlled invocation after two consumed failed
   attempts are proven not to reach `AIRuntimePort`;
7. permanently insufficient evidence leaves the old reservation immutable and
   `UNRESOLVED`, stops the old scope, and permits continuation only through a linked,
   human-authorized successor scope;
8. human-authorized successor-scope provenance is verified.

# Rejected alternatives

Using prompts, provider configuration, adapter metadata, or process-local counters as
enforcement is rejected because each can be bypassed or reset. Exposing Codex SDK
types as the canonical SDF contract is rejected: Codex-first does not mean
Codex-dependent. Treating every opaque provider request as the Phase-1 unit is
rejected because the SDF can govern only the controlled invocation exposed through
the runtime port.

Selecting a lower-level provider API solely for internal request granularity is
rejected because controlled-invocation accounting satisfies the accepted Phase-1
boundary. A universal provider framework, automatic routing, Graphify, remote
telemetry infrastructure, and multi-agent orchestration are deferred until measured
need exists.
