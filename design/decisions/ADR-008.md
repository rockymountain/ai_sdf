# Context

The initial M3 reporting implementation validated every `MeasurementWindow`
against the concrete GPT-5.6 Sol / medium control treatment. That treatment remains
the intended M3 experiment choice, but encoding it in the generic measurement
engine makes current experiment configuration behave like factory architecture.
This conflicts with SDF-P-006 and the CMP-003 / ADR-006 boundary, where runtimes are
replaceable and canonical telemetry, policy, and acceptance semantics remain
provider-neutral.

# Decision

1. Generic measurement and reporting code validates declaration structure,
   explicitness, provider-neutral vocabulary, and evidence consistency. It does not
   require one provider, model identifier, or reasoning tier.
2. Every measurement window explicitly declares its requested model,
   capability-aware requested reasoning effort, model-selection strategy, optional
   routing-policy version, context strategy, automatic-routing state, and
   context-optimization state. Omitted required keys are invalid.
3. `requested_model` is an explicit non-empty identifier. Requested reasoning
   effort is either an explicit non-empty capability value or explicit `null` when
   the runtime does not support or request that capability.
4. Model-selection and context strategies use the existing SDF vocabularies.
   Routing-policy version is explicit and nullable while routing is inactive; it is
   required when risk-routed or automatic routing is declared.
5. Invocation treatment evidence is compared with the treatment declared by its
   measurement window. Matching alternative-provider evidence may contribute;
   drift remains visible as profile inconsistency and blocks exact KPI eligibility.
6. A current experiment may deliberately select a concrete runtime, model, and
   reasoning value. That selection is declaration data and does not become a
   factory-wide provider invariant.
7. Provider-specific optional capabilities remain explicit rather than synthesized.
   Exact/unknown usage, evidence-boundary, attempt-linkage, outcome, completeness,
   and canonical-report semantics remain unchanged.
8. This correction requires no additional runtime adapter, `AIRuntimePort` change,
   telemetry schema migration, routing framework, or provider marketplace.

# Current M3 treatment

The intended M3 control treatment remains:

```yaml
requested_model: gpt-5.6-sol
requested_reasoning_effort: medium
model_selection_strategy: fixed
routing_policy_version: null
context_strategy: chat-heavy
automatic_model_routing: false
context_optimization: false
```

It must be supplied explicitly by a later approved M3 window declaration. This
decision neither declares that window nor selects its DEV set or evidence boundary.

# Historical compatibility

DEV-011 and TEST-011 remain truthful historical evidence for the then-locked M3
treatment. DEV-013 corrects the generic contract before the actual M3 measurement
window starts. Existing telemetry and reports are not rewritten or reinterpreted.

# Consequences

Alternative provider/model treatments can be represented and verified without
editing production measurement code, while within-window treatment drift still
fails closed for exact KPI eligibility. Provider neutrality does not require a
second provider implementation, and it does not weaken experiment comparability.
