# Context

FR-012 identifies two Factory-learning gaps: no mandatory disposition after a
material event, and no generic canonical mechanism to retrieve and apply
already-promoted lessons before material work with independent auditor
reassessment. `control/handoff/README.md`'s HO-I18/HO-I19 already prove the
Factory's working pattern for promoting a lesson into an operative rule
embedded in its governing document; LSN-003's `promoted_result` (`ADR-008`/
`DEV-013`/`TEST-013`) is the narrower, already-accepted measurement-contract
correction, distinct from LSN-003's own `preventive_heuristic` narrative,
which remains unpromoted as a general rule.

# Decision

1. **Learning-disposition triggers.** An independent-audit verdict is
   evidence, never a standalone disposition trigger. At a material
   correction round, the Owner-authorized correction actor records a
   provisional learning disposition and short rationale in that round's
   existing handoff. At CTRL-CHANGE delivery closure, or an Owner-issued
   non-delivery terminal outcome (`deferred`/`cancelled`) for a governed
   control decision, the authorized actor records a durable learning
   disposition with rationale in that same governed control-decision record.
   Work must never be marked complete or delivered merely to store a
   disposition. Blocked or merely paused work without an Owner-issued
   terminal decision remains open; its correction-handoff disposition stays
   provisional. A disposition never creates, validates, or promotes an LSN,
   and grants no implementation or closure authority.
2. **Disposition vocabulary.** `NEW_LEARNING_CANDIDATE`,
   `EXISTING_LEARNING_REINFORCED`, `NO_REUSABLE_LEARNING`. No value is a
   default; each requires a non-empty rationale.
3. **Disposition field shape.** `learning_disposition: {value: <enum>,
   rationale: <non-empty string>}`, validated against
   `knowledge/schemas/learning-disposition.schema.json`. This field is
   distinct from a control decision's existing `disposition` field
   (`delivered`/`deferred`/`cancelled`/etc.) and never replaces it.
4. **Applicability.** Before material T1/T2 design or implementation work, or
   material CTRL-CHANGE decision work (excluding T0 housekeeping and routine
   work), the executor checks `control/learning/` for promoted lessons whose
   `applicability` field matches the work, as a discovery aid only. For each
   match, the executor records the lesson and the concrete check derived
   exclusively from the accepted rule/control artifact identified by that
   lesson's `promoted_result` — never from its `observation`, `root_cause`,
   narrative, or `preventive_heuristic` fields. When no promoted lesson
   matches, the executor records a concise no-match rationale instead of a
   per-lesson list. Checking a lesson grants no authority to perform the
   work.
5. **LSN-003 clarification.** ADR-008 remains the accepted, narrower
   measurement-contract decision that is LSN-003's actual `promoted_result`.
   LSN-003's `preventive_heuristic` narrative is not thereby promoted into a
   Factory-wide rule. This ADR does not rewrite LSN-003 or ADR-008.
6. **Independent-auditor duty.** The auditor independently re-derives which
   promoted lessons' accepted rule/control artifacts apply to the work under
   review from `control/learning/` and their `promoted_result`, rather than
   accepting the executor's table, and verifies whether the resulting
   required concrete checks were actually performed. The auditor remains
   read-only, never edits a disposition record, and is granted no authority
   by this ADR.
7. **Canonical anchoring.** Both duties are added as role-conditioned prose
   invariants to the existing flat
   `constitution/agent-runtime.yaml:runtime_projection.invariants` list, and
   regenerated into `AGENTS.md` by the unmodified `tools/generate_agents.py`.
   CMP-005 documents this pre-existing projection boundary. No generator
   redesign, role-specific projection split, generic learning engine,
   LSN-per-event mechanism, or new runtime/provider architecture is
   introduced.
8. **Learning-contract clarification.** `control/learning/README.md`
   receives a minimal clarification: a learning disposition is tracking, not
   itself an LSN or authority; a promoted lesson's `promoted_result`
   identifies its operative rule/control; the LSN lifecycle (`observed ->
   validated -> promoted -> superseded`) is unchanged.

# Verification scope boundary

The Owner-selected verification boundary is
`MANUAL_PRESENCE_WITH_DETERMINISTIC_SHAPE`: learning-disposition creation is
an accountable actor duty (the correction or closure actor), not a
deterministic property. `knowledge/schemas/learning-disposition.schema.json`
and a corresponding shape-validating function in
`tools/traceability/validate.py` deterministically prove the prospective
`learning_disposition` shape is well-formed **when disposition evidence is
supplied to them**; they never prove that a disposition was actually created
or actually attached to a real closure/terminal record. This function is
intentionally **not** wired into `validate.py`'s unconditional
`main()`/`validate_traceability()` run against the live
`control/project-control.yaml`, because `control/*.yaml` is not currently
schema-governed by this validator at all, and unconditionally enforcing
presence against that live file would either retroactively fail pre-existing
decision records (backfilling, which this ADR does not authorize) or require
inventing an unapproved revision/cutoff policy to exempt historical records.
This ADR does not authorize a new live prospective enforcement gate, cutoff
rule, version migration, historical backfill rule, or new authoritative event
store; live enforcement against `control/project-control.yaml`, if wanted,
requires a separate governed change with its own architecture, decision,
implementation, and verification boundary. Whether required disposition
evidence is actually present in a real closure/terminal event remains an
accountable workflow/audit obligation for the independent auditor or another
actor authorized by the applicable closure process — a deterministic shape
PASS must never be reported as proof of that real-event presence. Presence
and shape correctness are therefore verified only as a deterministic,
directly-testable pure function in TEST-020, proven against representative
fixtures; they are not live-enforced by this change. Semantic correctness of
any lesson match, rationale, or disposition judgment remains independent-audit
and Owner-accountable, never claimed as deterministically proven.

# Compatibility and exclusions

This ADR does not retroactively require a disposition on any historical
control decision. It does not alter QG-001 through QG-006 semantics, the
`AIRuntimePort`/CMP-003 runtime boundary, or any existing measurement
contract. It does not accept, activate, or authorize Increment B (FR-009/
ADR-010/DEV-015), Increment C (FR-010/ADR-011/DEV-016), an M3 measurement
window or fixed set, or M4.
