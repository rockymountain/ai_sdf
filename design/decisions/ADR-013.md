# Context

The non-canonical Phase-1 working plan (`docs/phase1/phase1-plan.md` §7.1, §14.1)
names "average input tokens per accepted DEV task" as the primary M4
Graphify/context-treatment gate, with a required `>= 70%` reduction. At the time
that plan was written, only one runtime adapter existed, so that phrase referred
unambiguously to one thing.

CTRL-CHANGE-010/DEV-017 then added `ClaudeRuntimeAdapter` alongside
`CodexRuntimeAdapter`. FR-006's accepted delivery-accounting contract, implemented
in `src/ai_execution/cost_baseline.py`'s `input_tokens_per_accepted_dev` /
`total_tokens_per_accepted_dev`, correctly sums *every* attributable controlled
invocation for an accepted DEV — implementation, continuation, review, retries,
and failed attempts, across whichever adapters were actually used. That is exactly
right for delivery-cost accounting, and CTRL-CHANGE-011/DEV-018 depends on that
same all-attributable meaning continuing unchanged.

But an exact, all-attributable, mixed-provider total is not the same thing as a
provider-isolated, treatment-comparable context measurement. Reusing
`input_tokens_per_accepted_dev` as the literal M4 gate would silently conflate two
different questions: "what did this DEV cost in total attributable AI usage?" and
"did a declared context treatment reduce one provider's per-task context input,
holding everything else fixed?" LSN-003 already documents this class of mistake —
a coupling assumption in a generic contract that should instead be an explicit,
separately declared treatment configuration.

This ADR is a prospective, Owner-approved correction of the M4 KPI's intended
meaning, made before any M3 measurement window exists and before any M4 work is
authorized. It is not a metric rename of the existing delivery-accounting fields.

# Decision

## 1. Delivery accounting is unchanged

`input_tokens_per_accepted_dev`, `total_tokens_per_accepted_dev`, and the other
existing `cost_baseline.py` metrics keep their current, accepted, all-attributable
meaning: every controlled invocation attributable to an accepted DEV, across every
`invocation_purpose` and runtime adapter, including review, retries, failed
attempts, and continuations. `src/ai_execution/cost_baseline.py` is not modified by
this decision. An exact mixed-provider total remains valid accounting and
reconciliation evidence; it is never treated as a provider-independent comparison
scalar merely because it is exact.

## 2. A distinct, separately named M4 context-effect KPI

`src/ai_execution/context_effect.py` introduces a KPI with its own name and shape,
never reusing `input_tokens_per_accepted_dev` as its identifier:

```text
average_context_input_tokens_per_accepted_dev   (per predeclared cohort)
context_effect reduction (baseline -> treatment)
```

Its observation set is predeclared per cohort (baseline, treatment) as a
`ContextEffectCohort`: an explicit, non-empty, deduplicated accepted-DEV task list,
a machine-readable `evidence_boundary` (the existing `EvidenceBoundary` type,
reused unchanged from `cost_baseline.py`), explicit `task_eval_mix_id` /
`acceptance_criteria_id` identifiers, and an explicit `context_strategy`.

`context_strategy` is cohort identity, not incidental row metadata: every
contributing invocation must retain exactly the cohort's declared value, or that
cohort's observation set is `context_strategy_mismatch`. This is the opposite
requirement from `CompatibilityRule`, which deliberately excludes
`context_strategy` because it is the one condition expected to vary.

The M4 comparison direction is fixed, not an arbitrary pairing of two context
strategies: `baseline_cohort.context_strategy` must equal `chat-heavy`, and
`treatment_cohort.context_strategy` must be an already-governed, explicitly named
M4 context treatment — `manual-context-pack` or `graphify-context-pack` (Phase-1
plan §14.1; the canonical `context_strategy` vocabulary already names these).
`other` is never treatment-eligible: no governed declaration establishes what
concrete treatment it represents, so it fails closed rather than being accepted
merely because it differs from `chat-heavy`. A reversed pairing (treatment
declared as `chat-heavy` against a `chat-heavy` or non-eligible baseline) and a
same-strategy pairing both leave the KPI unavailable; neither can produce
`effect_gate_result=pass` on token-count differences alone. Broadening the
treatment-eligible set (including ever accepting `other`) requires a separate
governed decision, not an inference from this mechanism.

The numerator sums canonical `input_tokens` over every controlled invocation whose
`invocation_purpose` is `implementation` or `continuation`, attributable to a
cohort task, within the evidence boundary — including failures, retries, and
governed continuations. Controlled review usage is never included in this
numerator; it remains visible in existing delivery accounting
(`cost_baseline.build_report`) and in separate guardrail evidence.

The denominator is the number of DEV tasks in the predeclared cohort, not the
count of tasks with usable rows. Every declared task must be confirmed accepted
(`dev_outcomes.task_accepted=1`, finalized within the boundary) and have at least
one contributing invocation row; a task missing either makes the whole cohort's
observation set incomplete rather than silently shrinking the denominator.

Coverage reuses the existing `EvidenceBoundary` semantics unchanged — the same
half-open terminal-evidence rule `cost_baseline.build_report` already applies:
admissible evidence requires `started_at` in `[start_inclusive, end_exclusive)`
and `completed_at IS NOT NULL` and `completed_at < end_exclusive`. This decision
introduces no new evidence-window model. Coverage is evaluated over every
attributable `implementation`/`continuation` invocation whose `started_at` falls
in that window, regardless of terminal state — unlike `cost_baseline`'s
delivery-accounting query, which reports only admissible terminal evidence and is
unchanged by this decision. A non-terminal contributing invocation
(`completed_at IS NULL`) stays visible in coverage diagnostics; it makes the
cohort's observation set incomplete (`non_terminal_contributing_invocation`)
rather than silently disappearing. A contributing invocation that started in
range but completed at or after `end_exclusive` is a **boundary spill**: it is
terminal, but its terminal evidence falls outside this closed window. It also
stays visible (`boundary_spill_contributing_invocation`) and makes the
observation set incomplete; its later terminal evidence is never borrowed into
an already-closed window, the window is never extended, and the accepted-DEV
cohort is never shrunk to route around it. An invocation whose `usage_status` is
`exact` must satisfy
the same core-usage invariants used elsewhere in this factory — non-negative
integer `input_tokens`, `output_tokens`, `total_tokens`, with `total_tokens =
input_tokens + output_tokens` — or it is `malformed_exact_usage`: never treated
as usable evidence, never zeroed, never silently dropped, and always left visible
in the observation-set diagnostics.

Diagnostic collection is complete, not first-match: an eligibility failure in one
category (missing outcome evidence, missing invocation coverage, non-terminal
contribution, boundary spill, `context_strategy` or `requested_reasoning_effort`
drift, unknown usage, malformed exact usage, or rule incompatibility) never
truncates evaluation of the others. Every applicable category for a cohort is
collected in one pass — each list deterministically ordered and duplicate-free —
before a single primary `reason` is selected from a fixed priority order for
backward-compatible reporting. One defect must not hide another: a boundary-spill
invocation, for example, remains listed in diagnostics even when the same cohort
also has a non-terminal invocation, a missing accepted-DEV task, or missing
outcome evidence.

This applies per invocation as well as per cohort: diagnostics are evaluated
independently for every defect type whose evidence is admissible for that
invocation. A single admissible terminal invocation can violate more than one
dimension at once — for example `context_strategy` mismatch and malformed exact
usage together — and must then appear in every applicable diagnostic
collection. Eligibility filtering or primary-reason selection must not prevent
another applicable defect from being reported. Only an invocation with zero
applicable defects across every dimension contributes tokens to the exact sum.

## 3. Comparability is evaluated from retained evidence, per cohort pair

A single, explicitly supplied `CompatibilityRule` is checked against every
contributing row in both cohorts. It declares the runtime adapter, the covered set
of *observed* models (never requested model alone), the covered set of *observed*
runtime versions, an explicit `token_accounting_semantics` tag, the allowed
reasoning conditions, the required `model_selection_strategy`, and the required
`routing_policy_version`. `context_strategy` is deliberately excluded from the
rule: it is the treatment variable and is expected to differ between baseline and
treatment cohorts (e.g. `chat-heavy` vs. `manual-context-pack` or
`graphify-context-pack`).

For this KPI, reasoning effort is a fixed comparison condition, not a
set-membership condition: a `CompatibilityRule`'s `reasoning_conditions` must
declare exactly one permitted value, and construction fails closed if more than
one is supplied. `requested_reasoning_effort` is also a required, explicitly
supplied field on `ContextEffectCohort` — even when the declared condition is
null, so omission never silently becomes null — and
`baseline_cohort.requested_reasoning_effort` must equal
`treatment_cohort.requested_reasoning_effort` exactly, including both null.
Inferring equivalence between different reasoning-effort values is out of scope
and would require a separate, Owner-approved comparability decision.

A row satisfies the rule only when its `adapter_name`, non-null `observed_model`,
non-null `runtime_version`, `requested_reasoning_effort`,
`model_selection_strategy`, and `routing_policy_version` all match. An observed
model or version that is missing, or a requested-model match with a conflicting or
missing observed model, never satisfies the rule. A row's `requested_reasoning_effort`
must additionally match its own cohort's declared value exactly, independently of
the rule. Task/evaluation-mix and acceptance-criteria comparability are checked
once per cohort pair by requiring
`baseline_cohort.task_eval_mix_id == treatment_cohort.task_eval_mix_id` and the
same for `acceptance_criteria_id`.

If no `CompatibilityRule` is supplied, or any contributing row fails it, the
cohort's context-effect observation set is `not_comparable` and the KPI is
unavailable for that side. This mechanism creates no compatibility authority for
any real Claude or OpenAI runtime version: no populated real-world
`CompatibilityRule` is added by this change. A rule is data the caller supplies
from a separately governed, evidence-backed declaration; this decision ships only
the deterministic evaluation mechanism, exercised in `TEST-019` by synthetic
fixture rules that assert no real-version equivalence.

## 4. Three independently represented signals

`build_context_effect_report` returns three independent signals, matching the
Owner-approved contract:

- `effect_metric_calculable`: true only when both cohorts are complete
  (predeclared coverage, exact usage, rule-compatible) and comparable
  (task/eval-mix and acceptance-criteria match, a rule was supplied), and the
  baseline average is positive.
- `effect_gate_result`: `unavailable` whenever `effect_metric_calculable` is
  false; otherwise `pass` or `fail` against the Owner-approved `>= 70%` reduction
  threshold carried forward from the Phase-1 plan's stated M4 gate, now made
  canonical by this decision. The comparison uses exact integer cross-
  multiplication (`10 * treatment_sum * baseline_count <= 3 * baseline_sum *
  treatment_count`), and the reported reduction is an exact `fractions.Fraction`
  rendered as `numerator/denominator`; no binary floating-point arithmetic decides
  the boundary.
- `treatment_decision_eligible`: true only when `effect_metric_calculable` is true
  **and** a `GuardrailContract` was supplied whose declared required evidence keys
  are all present and non-null in the supplied guardrail evidence. A missing
  `GuardrailContract`, and an explicitly supplied `GuardrailContract` with an
  empty required-key set, both always yield `treatment_decision_eligible = false`
  — an absent authority and an empty one are both authority gaps, never vacuous
  permission. This decision ships no real M4 guardrail set. A caller must supply
  one from a separately authorized guardrail declaration, which does not yet
  exist.

A passing gate does not imply decision eligibility (missing guardrails), and a
failing gate does not imply ineligibility (a well-evidenced rejection is still a
decision). Neither state accepts, rejects, or authorizes anything by itself: the
Project Owner retains the final treatment decision and M4 authorization.

## 5. No expansion beyond the declared boundary

This decision does not change `AIRuntimePort`, invocation-purpose authority,
capability derivation, reservation/mutation semantics, or the operational
telemetry schema. It adds no generic provider-normalization framework, automatic
runtime routing, role registry, or second accounting system; Claude/Codex
usage-field interpretation stays inside their adapters exactly as CMP-003 already
requires. It does not declare an M3 measurement window or fixed task set, execute
baseline tasks, activate DEV-014/DEV-015/DEV-016, authorize M4, or make any
treatment-acceptance decision.

# Prospective qualification and precedence

This ADR prospectively qualifies, from this decision's boundary forward, how the
non-canonical Phase-1 plan's §7.1/§14.1 "average input tokens per accepted DEV
task" M4 gate description is realized: as the distinct `context_effect` KPI in
`src/ai_execution/context_effect.py`, not as the existing delivery-accounting
`input_tokens_per_accepted_dev` field. It does not retroactively reinterpret any
already-recorded metric, report, or accepted DEV: DEV-011/TEST-011 (the locked M3
chat-heavy treatment) and DEV-013/TEST-013 (the provider-neutrality correction)
remain truthful, unrewritten historical evidence of the delivery-accounting
contract as it existed before this decision. The Phase-1 plan itself remains
non-canonical supporting material and is updated only if needed for consistency;
it is not amended to assert new authority.

# Historical compatibility

No M3 measurement window has been declared, and no context-effect observation has
ever been produced. There is therefore no existing context-effect report or
decision to preserve compatibility with. `input_tokens_per_accepted_dev`,
`total_tokens_per_accepted_dev`, and every other existing `cost_baseline.py` field
and report shape are unmodified; `REPORT_SCHEMA_VERSION` in `cost_baseline.py` is
unchanged. The new context-effect report shape is independently versioned as
`CONTEXT_EFFECT_REPORT_SCHEMA_VERSION = 1`.

# Consequences

A future M3/M4 measurement window can declare a real `CompatibilityRule` and a
real `GuardrailContract` as separate, explicit, evidence-backed governed
decisions, and can then produce a context-effect result whose calculability, gate
result, and decision eligibility are independently auditable and never silently
conflated with delivery-accounting totals. Until those real declarations exist,
`context_effect_report` calls without them are correctly `unavailable` /
`treatment_decision_eligible=false`, by construction rather than by omission.
