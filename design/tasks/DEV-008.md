# Scope

Implement the locked PROB-002 / FR-006 / FR-007 / NFR-002 / CMP-003 /
ADR-006 chain. Canonical `autonomous_execution.max_attempts: 2` is explicitly
authorized by the Project Owner's DEV-008 implementation request; the existing
600-second watchdog remains unchanged. TEST-008 records deterministic evidence.

The provider-neutral `BoundedExecutionController` registers a stable workflow
objective, allocates reservations, records deterministic checkpoints, resolves
uncertain evidence with human authorization, and creates linked successor scopes.
`ControlledInvocationGateway` guards every purpose before `AIRuntimePort.start`.
SQLite schema 3 adds scope accounting alongside existing invocation and DEV-outcome
evidence, with transactional upgrades from schema 1 and 2.

# Workflow contract

Use a stable `objective_id` within the DEV task when registering a scope through
`create_scope`. Changing run, process, provider session, or source revision does
not establish a new objective. An objective that already has a registered scope
requires `successor_scope`, with recorded actor, timezone-qualified timestamp,
reason, disposition, and predecessor linkage. Objective identity and human
authorization are supplied by the trusted workflow, not inferred from prompt text.

Call `reserve` and pass its `reservation_id` and `candidate_attempt_number` into
an implementation `ControlledAIInvocation`. Omit `attempt_number` until affirmative
start evidence consumes the reservation. Invoke through the gateway; then supply
a `CheckpointEvidence` containing the actual deterministic command, exit code,
and retained evidence reference to `close_attempt`. Invocation success alone
leaves the attempt open. A failed final checkpoint atomically opens the circuit.

The `RuntimeStartControl.report_start` port boundary accepts provider-neutral
`StartEvidence`. Accepted execution consumes the reserved candidate; definite
non-start releases it; absent or uncertain evidence retains it as unresolved.
After terminal uncertainty, `resolve_reservation` requires human authorization
and affirmative evidence. Human resolution cannot race a live invocation.

Only interrupted/usage_limit evidence suspends an attempt. Continuation carries
the same scope, objective and attempt, a new invocation ID, predecessor invocation
ID, and `HumanAuthorization`. It cannot allocate another reservation or resume a
closed checkpoint. Recovered usage-limit evidence is appended separately rather
than rewriting the predecessor's terminal or usage record.

# Adapter conformance mapping

For the pinned Codex adapter, a returned `thread.turn` handle is affirmative
acceptance. Local failure before that request is definite non-start. A failed
request without a handle is uncertain, including a response lost after dispatch.
The gateway retains the reservation in that case. Implementation and authorized
continuation use the workspace-write capability; other purposes stay read-only.
Provider SDK types remain in the adapter. Continuation may start a new runtime
session; SDF lineage and the consumed attempt remain authoritative.

# Boundaries

No DEV-009 work, control changes, design rebaseline, automatic continuation,
same-scope reset, automatic routing, or new checkpoint/replay subsystem is included.
Authorization records and checkpoint references are trusted workflow inputs; the
controller validates their structure and linkage, not the human's identity or the
truth of external evidence. A process dying before terminal evidence leaves its
durable claim unavailable until evidence is recovered. No live provider invocation
is needed for the deterministic M2 proof.
