# Purpose

Implement `ADR-013`: a separately named, separately structured M4 context-effect
KPI (`src/ai_execution/context_effect.py`), so that a future context-treatment
decision cannot be made by silently reusing the existing delivery-accounting
`input_tokens_per_accepted_dev` field as if it were a provider-comparable,
treatment-isolated context measurement.

# Upstream intent

- `FR-006`
- `FR-011`
- `CMP-003`
- `ADR-006`
- `ADR-012`
- `ADR-013`

No new FR or CMP is introduced; existing accepted intent and architecture are
reused. `ADR-013` is the new decision this task implements.

# T2 implementation boundary

DEV-019 is limited to:

- `src/ai_execution/context_effect.py`: `CompatibilityRule`, `ContextEffectCohort`,
  `GuardrailContract`, `CohortObservation`, and `build_context_effect_report`;
- predeclared-cohort evaluation: every declared accepted-DEV task must be confirmed
  accepted (`dev_outcomes.task_accepted=1`, finalized within the evidence boundary)
  and have at least one contributing `implementation`/`continuation` invocation row;
  a missing task makes the cohort's observation set incomplete rather than shrinking
  the denominator;
- coverage reusing the existing `EvidenceBoundary` half-open terminal-evidence
  rule unchanged (`started_at` in range, `completed_at IS NOT NULL`,
  `completed_at < end_exclusive`) over every attributable contributing
  invocation regardless of terminal state; a non-terminal row
  (`completed_at IS NULL`) or a boundary-spill row (terminal at/after
  `end_exclusive`) both stay visible in coverage diagnostics and make the
  cohort incomplete rather than disappearing or borrowing later evidence into a
  closed window;
- canonical exact-usage validity for contributing rows — non-negative integer
  `input_tokens`/`output_tokens`/`total_tokens` with `total_tokens = input_tokens +
  output_tokens` — reimplemented locally so `cost_baseline.py` stays unmodified;
  malformed exact usage is never treated as usable, never zeroed, and never
  silently dropped;
- a numerator over canonical `input_tokens` for every contributing
  `implementation`/`continuation` invocation, including failures, retries, and
  governed continuations; controlled review usage is never included;
- `context_strategy` as explicit, validated cohort identity: every contributing
  invocation must retain the cohort's declared value; the M4 comparison
  direction is fixed as baseline `chat-heavy` against an already-governed named
  treatment (`manual-context-pack` or `graphify-context-pack`) — never an
  arbitrary or reversed pairing, and never an undeclared `other` — or the KPI is
  unavailable;
- `requested_reasoning_effort` as a required, explicitly supplied cohort
  declaration (even when null — omission never silently becomes null): a fixed
  comparison condition, not a set-membership one. Baseline and treatment must
  declare the identical value, every contributing invocation in both cohorts
  must match its own cohort's declared value, and a `CompatibilityRule`
  declaring more than one permitted reasoning-effort value is invalid and fails
  closed at construction;
- deterministic, evidence-backed comparability: a single explicit
  `CompatibilityRule`, checked against retained `observed_model`, `runtime_version`,
  `requested_reasoning_effort`, `model_selection_strategy`, and
  `routing_policy_version` evidence for every contributing row, plus cohort-pair
  `task_eval_mix_id`/`acceptance_criteria_id` equality; `context_strategy` is
  deliberately excluded from the rule itself, for the opposite reason it is
  required as cohort identity above;
- complete diagnostic collection, per cohort and per invocation: an eligibility
  failure in one coverage category never truncates collection of the others,
  and every applicable dimension is evaluated independently over the same
  admissible-row set rather than a narrower subset already filtered by another
  dimension's result — so a single row with more than one independent defect
  (e.g. `context_strategy` mismatch and malformed exact usage together)
  appears in every applicable diagnostic collection. Every applicable
  diagnostic (missing outcome evidence, missing coverage, non-terminal,
  boundary spill, strategy/reasoning drift, unknown/malformed usage, rule
  incompatibility) is gathered in one pass, deterministically ordered and
  duplicate-free, before a single primary `reason` is selected from a fixed
  priority order; only a row with zero applicable defects contributes tokens;
- three independently represented signals — `effect_metric_calculable`,
  `effect_gate_result`, `treatment_decision_eligible` — computed with exact
  `fractions.Fraction`/integer-cross-multiplication arithmetic against the
  Owner-approved `>= 70%` reduction threshold; no binary floating-point rounding
  decides the boundary;
- a `GuardrailContract` mechanism that evaluates supplied evidence against an
  explicitly declared required-key set; a missing contract and an explicitly
  empty required-key set both always yield `treatment_decision_eligible=false`;
- reuse of `cost_baseline.EvidenceBoundary`, `BaselineEvidenceError`, and
  `SUPPORTED_EVIDENCE_SCHEMA_VERSIONS` unchanged;
- deterministic verification under `TEST-019`, using synthetic fixture rows and a
  temporary read-only SQLite database.

`src/ai_execution/cost_baseline.py` is not modified: its existing metrics, report
shape, and `REPORT_SCHEMA_VERSION` are unchanged. `AIRuntimePort`, the gateway,
controller, and operational telemetry schema are unchanged.

# Exclusions

DEV-019 does not:

- declare an M3 measurement window, a fixed M3 task set, or execute any baseline
  task;
- activate `DEV-014`/`DEV-015`/`DEV-016`;
- authorize M4 or make any treatment-acceptance decision; a passing gate never
  implies `treatment_decision_eligible`, and a failing gate never implies
  ineligibility — both remain independently represented, and only the Project
  Owner decides;
- ship a populated `CompatibilityRule` covering any real Claude or OpenAI runtime
  version, or a populated real M4 `GuardrailContract`; only the deterministic
  mechanism is delivered, exercised by synthetic fixtures in `TEST-019`;
- redefine `input_tokens_per_accepted_dev`/`total_tokens_per_accepted_dev` or hide
  an exact mixed-provider delivery total;
- rewrite historical telemetry, or DEV-017/DEV-018/DEV-011/DEV-013 history;
- perform a live Anthropic or OpenAI inference call, use
  `tools/ai_execution.py` or an equivalent governed runtime operator to execute
  this DEV, create a reservation, or create an implementation attempt.
