# Project Control History Operating Contract

## 1. Purpose

`control/history/` lưu các project-control records cần tồn tại như các named,
durable historical artifacts ngoài Git commit history thông thường.

Mục tiêu của namespace này là bảo đảm:

- project-control decisions có thể được handoff giữa người, agent và môi trường;
- rebaseline history không bị mất khi current control state được cập nhật;
- project history có thể đọc được trên Windows, Linux và macOS;
- automation không phụ thuộc absolute local paths;
- future agents có thể hiểu khi nào cần tạo history artifact và khi nào không.

`control/history/` không phải event log cho mọi commit.

Git vẫn là historical record cấp repository.

---

# 2. Authority boundary

History artifacts MAY record:

- accepted project baselines;
- approved rebaselines;
- material scope-control decisions;
- material budget-control decisions;
- material timeline-control decisions;
- milestone-control snapshots khi cần cho audit/handoff;
- project-control exceptions có human approval.

History artifacts MUST NOT override:

- `design/problems/*`;
- `design/requirements/*`;
- `design/architecture/*`;
- `design/decisions/*`;
- `constitution/*`;
- `knowledge/traceability.yaml`;
- source/test/runtime evidence.

Nếu history artifact mâu thuẫn với canonical hoặc runtime evidence,
canonical/runtime evidence thắng và history artifact phải được corrected hoặc
superseded.

---

# 3. What belongs here

Tạo named history artifact khi có một material control event như:

```text
initial project baseline accepted
material project rebaseline approved
scope boundary materially changed
budget envelope materially changed
timeline commitment materially changed
milestone materially replanned
control exception accepted
handoff requires a stable named control snapshot
```

Ví dụ:

```text
control/history/
├── README.md
├── CTRL-BASELINE-001.md
├── CTRL-REBASELINE-001.md
└── CTRL-REBASELINE-002.md
```

---

# 4. What does NOT belong here

Không tạo history artifact cho:

* mỗi commit;
* mỗi DEV status update;
* mỗi CI run;
* mọi thay đổi nhỏ của forecast;
* token telemetry raw;
* runtime database dumps;
* duplicate copies của ADR/DEV/TEST;
* autogenerated reports không có control decision.

Các thay đổi routine nên được thể hiện qua:

* Git history;
* current `control/project-control.yaml`;
* canonical artifacts;
* operational telemetry.

Lean rule:

> Không tạo history artifact nếu không có một durable control decision,
> audit need hoặc handoff need phụ thuộc vào nó.

---

# 5. Artifact identity

Mỗi history artifact MUST có stable identity.

Recommended namespaces:

```text
CTRL-BASELINE-NNN
CTRL-REBASELINE-NNN
CTRL-SNAPSHOT-NNN
CTRL-EXCEPTION-NNN
```

Ví dụ:

```yaml
---
id: CTRL-REBASELINE-001
kind: project-rebaseline
title: Phase 1 Delivery Rebaseline
status: accepted
version: 1
owner: factory-maintainer
effective_date: 2026-10-01
---
```

ID không được tái sử dụng cho một decision khác.

---

# 6. Baseline history semantics

Một baseline hoặc rebaseline artifact SHOULD record tối thiểu:

```text
previous baseline
new baseline
reason
scope impact
budget impact
timeline impact
risk impact
approval
effective date
evidence
```

Không silently replace historical values.

Ví dụ:

```text
original baseline
    ↓
rebaseline 001
    ↓
rebaseline 002
    ↓
current project-control state
```

Mỗi bước phải recover được từ Git.

---

# 7. Current state vs history

`control/project-control.yaml` là current operational control state.

`control/history/*` là durable historical decisions/snapshots.

Do not treat them interchangeably.

Rule:

```text
project-control.yaml
    = what is true now

history/
    = what was explicitly baselined, rebaselined,
      accepted or preserved for audit/handoff
```

Một history artifact không tự động trở thành current state.

Current state phải được cập nhật riêng khi decision có hiệu lực.

---

# 8. Snapshot rule

Control snapshots MAY được tạo cho:

* major phase boundary;
* major milestone closure;
* external audit;
* major handoff;
* pre/post material rebaseline.

Snapshots SHOULD NOT được tạo theo lịch máy móc nếu không có consumer.

Snapshot filename example:

```text
CTRL-SNAPSHOT-001.md
```

Snapshot MUST state:

```text
snapshot purpose
source revision
control revision
scope state
budget state
timeline state
active risks
current milestone
known unknowns
```

Snapshot không thay thế current project control state.

---

# 9. Cross-platform path rules

All repository paths in history artifacts MUST:

* use repository-relative paths;
* use forward slashes `/`;
* never contain local absolute paths;
* never depend on a specific drive letter;
* never depend on a user's home directory.

Correct:

```text
design/decisions/ADR-006.md
control/project-control.yaml
src/ai_execution/gateway.py
```

Incorrect:

```text
D:\Docs\ai_sdf\design\decisions\ADR-006.md
C:\Users\name\project\...
/Users/name/project/...
```

Markdown links SHOULD use repository-relative paths.

Example:

```markdown
[ADR-006](../../design/decisions/ADR-006.md)
```

This rule exists to preserve:

* Windows compatibility;
* Linux/macOS compatibility;
* CI portability;
* GitHub rendering;
* agent handoff portability.

---

# 10. Encoding and file-format rules

Text artifacts SHOULD use:

```text
UTF-8
LF line endings where repository tooling normalizes them
plain Markdown or YAML
```

History semantics MUST NOT depend on:

* platform-specific text converters;
* proprietary document formats;
* local shell behavior;
* local environment variables.

If machine-readable data is required, prefer YAML or JSON.

---

# 11. Git revision references

When recording repository evidence, prefer full commit SHA for durable history.

Example:

```text
f269bb29d5f7bc91a677b6ec4d46dedbffc877dd
```

Short SHA MAY be shown for readability but MUST NOT be the only durable
identifier when ambiguity matters.

Do not assume branch names are immutable historical references.

---

# 12. Time representation

Dates SHOULD use ISO format:

```text
YYYY-MM-DD
```

When exact time matters, use timezone-aware ISO 8601.

Example:

```text
2026-09-21T09:30:00+07:00
```

Do not invent timestamps that were not captured.

If only date is known, store only the date.

---

# 13. Unknown and incomplete historical evidence

History artifacts MUST preserve uncertainty.

Use explicit states such as:

```text
unknown
not_measured
not_available
not_yet_baselined
incomplete
```

Do not infer:

```text
unknown → 0
unknown → false
unknown date → guessed date
unknown effort → estimated effort
```

Historical Phase-0 AI usage is a known example of incomplete evidence and MUST
remain represented as such.

---

# 14. Handoff contract

A future human or agent taking over the project SHOULD be able to reconstruct
project-control state by reading, in order:

```text
control/README.md
control/roadmap.md
control/project-control.yaml
control/history/README.md
relevant latest history artifact(s)
```

Then consult canonical authorities as needed:

```text
constitution/*
design/*
knowledge/traceability.yaml
source/tests
runtime evidence
```

A handoff MUST NOT require knowledge of:

* previous chat history;
* local absolute paths;
* undocumented shell commands;
* one specific AI provider.

---

# 15. Handoff minimum context

When a named handoff snapshot is needed, it SHOULD identify at least:

```text
current main revision
current phase
current milestone
latest completed milestone
active baseline IDs
remaining near-term scope
budget coverage
timeline forecast
open blockers
open material risks
next human decision
next intended DEV/task
```

Do not copy the entire repository context into a handoff artifact.

Link to canonical evidence instead.

---

# 16. Rebaseline workflow

A material rebaseline follows:

```text
detect variance / scope change
        ↓
analyze impact
        ↓
propose new baseline
        ↓
human approval
        ↓
create history artifact
        ↓
update project-control.yaml
        ↓
continue delivery
```

Automation MAY prepare or validate the proposal.

Automation MUST NOT approve a material rebaseline on behalf of the accountable
human.

---

# 17. Supersession

A historical artifact SHOULD normally remain immutable after acceptance except
for factual correction.

If its control decision is replaced:

```text
old artifact:
  status: superseded

new artifact:
  references predecessor
```

Do not delete the old accepted record merely because a new baseline exists.

---

# 18. Naming rules

Use deterministic filenames matching artifact IDs when practical:

```text
CTRL-BASELINE-001.md
CTRL-REBASELINE-001.md
CTRL-SNAPSHOT-001.md
CTRL-EXCEPTION-001.md
```

Avoid names such as:

```text
latest.md
new-plan.md
final-final.md
updated-roadmap.md
```

Current state already has a stable location:

```text
control/project-control.yaml
```

---

# 19. Automation rules

Future automation MAY:

* detect stale current control state;
* derive actual milestone evidence;
* calculate deterministic variances;
* propose history artifacts;
* validate IDs and references;
* generate handoff summaries.

Future automation MUST NOT:

* invent missing historical evidence;
* silently rebaseline;
* silently mark milestone success;
* overwrite accepted history;
* convert forecasts into commitments;
* change human-owned material decisions.

---

# 20. Initial state

At creation of this namespace:

```text
accepted named project baseline:
  none yet

accepted rebaseline:
  none

current control state:
  control/project-control.yaml

roadmap:
  control/roadmap.md

next expected history artifact:
  CTRL-BASELINE-001
```

`CTRL-BASELINE-001` SHOULD be created only after the initial Scope / Budget /
Timeline baseline has been explicitly reviewed and accepted.

Until then, absence of that artifact is intentional.
